# Decisions and deviations from the spec

The spec (docs/spec.md, originally titled "Salon") is followed unless listed here.

| Area | Spec | What we did | Why |
|---|---|---|---|
| Name | Salon | **Docent** | Owner preference. |
| Local database | Supabase | PGlite (embedded Postgres) when `DATABASE_URL` is unset; postgres-js otherwise | Zero setup locally, same Drizzle schema and SQL in prod. |
| Auth (R1) | Google + email magic link | Guests by default (signed cookie). Sign-in by **6-digit email code** (Resend) or Google (hand-rolled OAuth code flow, no SDK). First sign-in upgrades the guest in place; signing into an existing account merges the guest into it | A magic link opens in Safari, not in the installed iOS app (separate cookie jars), so a code is the only flow that works there. Codes are HMAC-hashed, single-use, 10-minute, 5 attempts; rate-limited per email and IP. |
| SPARQL endpoint | WDQS only | The pool scan goes to QLever's public Wikidata mirror first (WDQS as backup); every other query goes to WDQS first (QLever on timeout) | The pool query scans all ~1.1M paintings' sitelink counts, which WDQS has no index for (35–60 s, often times out). QLever answers it in ~2 s. Disable with `WIKIDATA_FALLBACK_ENDPOINT=""`. |
| Movement holdings | Counted from Wikidata | Derived: Σ artist holdings over artists in that movement | No extra queries; good enough for ranking. |
| Duplicate museums | Merge within 200 m | Within 200 m **and** sharing a distinctive name token (or <5 m apart) | Plain 200 m would merge neighbours like Berlin's Museum Island buildings. |
| Museum departments | — | Items with ≤5 sitelinks that are "part of" (P361) a better-known museum within 200 m roll up into it | Wikidata files most Louvre paintings under "Department of Paintings of the Louvre". |
| Ingestion scheduling | Each pass as its own serverless call | One run fetches everything, then writes in a single transaction. GitHub Actions nightly job is the primary scheduler; `/api/cron/ingest` exists for Vercel Cron | A failed run can never leave half-written data; GH Actions has no tight time limit. |
| Typed-city location | Free text | Offline list of ~45 art cities + browser location + "anywhere" | No geocoding API call at request time. |
| Map tiles | OSM light style | OSM standard tiles with a CSS filter (desaturated light / inverted dark) | CARTO's free basemaps now require an API key. |
| Pool size | ≥15 sitelinks, "a few thousand" | **≥8 sitelinks ≈ 2,470 paintings** (≥15 gave only ~700). Set `POOL_MIN_SITELINKS` to tune. The seed uses ≥10 (~1,600) | Counts on 2026-11-11: ≥5: 5,270 · ≥8: 2,563 · ≥10: 1,650 · ≥15: 696 (before image/artist/label filters). |
| Fame | sitelinks | `artworks.fame` = 0.6 × percentile(60-day English Wikipedia pageviews) + 0.4 × percentile(sitelinks). Pageviews come from the MediaWiki API (`prop=pageviews`, 50 titles/request, following `pvipcontinue`, honouring 429 `Retry-After`) | Sitelinks measure breadth, not recognisability. The per-article REST endpoint throttled to ~73 min for 1,600 titles; the batched API takes ~10 min with a generic User-Agent (set `INGEST_USER_AGENT` with a contact to be throttled less). |
| Taste dimensions | artist, movement | + **genre/subject** (Wikidata P136, on 94% of pool paintings vs 55% for movement) + **century** (from year) | Genre is the best-populated signal Wikidata has. |
| Prediction | 5 + 5·tanh(A + 0.5·M̄) | 5 + 5·tanh(0.6·(A + 0.5·M̄ + 0.35·Ḡ + 0.2·P)); low confidence only if artist, movements and genres are all unknown. The 0.6 keeps strong matches distinguishable (~9.6–9.8) instead of all reading 10.0; it's monotone, so ordering is unchanged | `pnpm eval:algo`, 300 simulated users × 25 rankings, Spearman on 300 held-out paintings: mixed taste 0.309 → **0.369**; subject-driven 0.224 → **0.447**; artist-driven 0.279 → 0.267. |
| Museum match | holdings terms × distance | + hidden **masterpiece term**: 0.5 × Σ over the top-5 confident predictions >6.5 of the works there of (ŝ−5)/5. Two passes: holdings shortlist (3× limit), then re-rank. Candidate works are pre-filtered in SQL to liked artists/movements/genres (~90 ms on PGlite for the demo user) | Holdings say "lots of Monets"; this rewards "and the specific ones you'd love hang here". |
| **Core flow** | Rank famous paintings from a queue | **Visits only (Beli-style).** Log a museum visit → upload the photos you took → say which painting each shows → rank only those. The catalogue still powers identification, taste and museum recommendations | Owner decision 2026-11-11: everything you rank is something you stood in front of. |
| Identifying photos | — | Pick from that museum's catalogued paintings (search box), or search the whole catalogue (loans), or add it by hand (title + optional artist). No AI recognition | Free, always right, $0 budget. Hand-added paintings (`artworks.owner_id`, id `X…`, artist placeholder `X0`) rank like any other but never shape taste and are invisible to other users. |
| Photo handling | — | Resized in the browser (max 2000 px + 480 px thumbnail) and re-encoded as JPEG, which strips EXIF including GPS. Served only to their owner via `/api/photos/[id]`. Storage driver: local disk (`PHOTO_DIR`) or any S3-compatible bucket (`STORAGE_DRIVER=s3`; R2 recommended), private, owners get 1-hour signed URLs | R2's free tier has no egress fees, which matters for an image-heavy app. |
| Ranking rule | — | `insertRanking` refuses a painting the user has no photo of (`403 not_photographed`) | Enforces "visits only" on the server, not just in the UI. |
| Logging a visit | — | Also marks the museum "Been there", so recommendations point to new museums | |
| Queue | 70% predicted / 30% unseen movements | **Superseded by visits:** /rank now works through your identified, unranked photos (newest visit first). The queue algorithm (`lib/algo/queue.ts`) and its tests are kept but unused | |
| Taste page | top artists + movements | + subjects, eras, and "Not your thing" (negative affinity resting on 2+ paintings) | |
| Taste page | — | Hidden until 3 rankings | A profile from 1–2 paintings is noise. |
| Mobile app | — | **PWA**, not native: manifest, icons, service worker, bottom tab bar, safe-area insets, 16 px inputs (no iOS zoom), haptics on Android | $0, one codebase, installable on both platforms. Capacitor can wrap it later for store listings ($99/yr Apple account). |
| Adding photos | Log visit → upload | **Photo-first**: + opens the library; date and GPS are read from EXIF in the browser; photos are grouped by day and ~1 km (`lib/algo/visitGroups.ts`); the museum is suggested (nearest within 1.5 km); same museum + day reuses the visit. No GPS but taken today → current location | iOS often strips GPS from Safari-picked photos, hence the current-location fallback. |
| Uploads | — | Queued in IndexedDB as resized JPEGs, 2 at a time, retried on reconnect / foreground / backoff; 4xx (except 429) stops with a message | Museum Wi-Fi is bad; a plain upload would lose photos. |
| Notifications | — | Web Push (VAPID). Daily cron reminds once per visit, ≥12 h after logging, if anything is left to identify or rank | iOS supports web push only for installed apps (16.4+); the account page explains. |
| Rate limits | — | Postgres table of events (sliding window), pruned daily | No Redis to run or pay for. |
| Production config | — | `lib/env.ts` validates every setting; production start fails listing what's missing. `vercel-build` migrates before building; postgres-js uses 1 connection per serverless instance with `prepare:false` for poolers | |
| Demo account | — | Read-only for visits and photos, reset nightly by the daily cron | It's shared by everyone who taps it. |
| Nudity | — | `artworks.nudity` = Wikidata depicts (P180) an item labelled nudity/naked/nude/breast/genitals (not "breastfeeding") **or** genre nude/erotic art: 187 of 1,580 pool paintings (genre alone: 129). Used three ways: (1) **"Hide nudity" setting**, a hard rule: filtered from museum suggestions, "what to see" lists and predictions; blurred on artwork pages and in the identify list; own photos untouched. (2) A **content dimension** in taste (affinity learned only from tagged paintings, weight 0.6 in prediction), so ranking nudes low lowers every nude's prediction, whatever the artist or genre, and shows "Nudity" under "Not your thing" with an offer to turn the rule on. (3) The shared demo and landing page never show it | Nudity cuts across genres ("mythological painting", "religious art"), so the genre dimension couldn't express "no nudity". Wikidata is incomplete (e.g. *The Garden of Earthly Delights* isn't tagged), which is why learning from rankings complements the rule. |
